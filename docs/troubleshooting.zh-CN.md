# 连接问题排查

[English](./troubleshooting.md)

## 收集连接日志

在双方浏览器 Console 中开启 Info、Warning 和 Preserve log，按 `[Peerto connection]` 过滤后复现。日志带有匿名客户端标记、尝试/连接计数、分配角色、当前 ICE/SDP 状态、操作耗时与脱敏错误类别。

- `ws_connect/open/close`、`ws_timeout` 和 `ws_message_failed` 用于定位信令或认证阶段失败；房间消耗后的关闭可能是正常释放。
- `sdp_create_offer/answer`、`sdp_set_local` 和 `sdp_set_remote` 分别记录 `_start`、`_ok`、`_failed`。失败时记录浏览器错误类别及可用的 SDP 错误行号，不记录 SDP 原文。
- `local_candidate`、`remote_candidate` 和 `ice_add_candidate_failed` 区分采集、排队/过期候选与添加失败。单个 `ice_candidate_error`（包括 701）不等于整条连接失败，需要结合其他候选和最终 ICE 状态判断。
- `ice_restart` 和 `previous_path_*` 区分新协商与旧路径复用；进入失败状态后仍需手动重试。

每个客户端仅在内存保留最近 200 条记录，并输出到浏览器 Console，不上传服务器。不记录原始 SDP、候选地址/端口、URL、设备名称/密钥、Token、聊天或文件内容。排查时只分享筛选后的连接记录，不要直接分享未经检查的全部浏览器日志。

## 二维码链接与剪贴板附件

在连接码过期前扫描“连接另一台设备”中的二维码；它由同源分享链接在本地生成。新浏览器必须同意授权 Cookie/本地存储并设置本机名称，邀请会跨越这些步骤保留，身份就绪后才消费。老浏览器沿用自己的身份和名称。在不同浏览器或内置浏览器中打开会使用不同的存储空间，想保持同一设备应使用同一浏览器；不会跨设备复制 Cookie 或私钥。

在消息输入框使用浏览器的正常粘贴操作。文字仍可编辑；浏览器提供的文件/截图会进入确认弹窗，也可通过附件按钮多选。可移除或取消，只有确认后才加入发送队列。每条连接最多排队 32 个文件，依次传输。切换会话会清空未确认附件，断线会取消已排队传输且不会自动重发。如果浏览器/系统只提供文字或文件路径而不提供文件内容，无法通过粘贴读取该文件，请改用文件选择器。

## 一直显示无法建立直连

常见原因有：

- 双方都在对称 NAT 后
- 运营商使用 CGNAT
- 公司或校园网络限制 UDP
- 两台设备在同一出口 NAT 后，但路由器不支持 hairpin
- 防火墙丢弃 WebRTC 使用的随机 UDP 端口
- 公共 STUN 在当前网络不可达

如果选择使用 TURN，可在设置中保留 UDP 和 TCP 两种 URL，然后点击会话输入区的“重试连接”。不使用 TURN 时，先检查下文的局域网、UDP、防火墙与 STUN 可达性。

STUN 只帮助发现地址，不转发数据。增加更多 STUN 不能解决所有 NAT 问题。

## 两台设备在同一局域网仍然连不上

浏览器通常会收集 host Candidate，但 mDNS、访客 Wi-Fi 隔离、AP Client Isolation 和主机防火墙都可能阻止互访。

可以逐项检查：

1. 两台设备是否能在局域网直接访问彼此。
2. Wi-Fi 是否开启了客户端隔离。
3. VPN 是否改写默认路由。
4. 浏览器是否允许 WebRTC。
5. 防火墙是否允许浏览器的 UDP 流量。

## 连接码生成成功，但另一台设备找不到主机

Host 仍需凭证与设备私钥验证，但不再仅因 HTTP 与 WSS 出口 IP 不同而被拒绝。切网若导致会话掉线，请在输入区点击“重试连接”；普通配对码过期则需要重新生成。

检查两台设备的系统时间、HTTPS 证书和 WebSocket。反向代理必须正确处理 `/ws` Upgrade。

## 刷新后无法恢复

恢复需要双方仍保存：

- 同一配对码命名空间
- 相同的高熵恢复令牌
- 自己的 P-256 私钥
- 对方的设备身份

双方可以按任意顺序或同时点击“重试连接”。上次已认证的传输仍被保留时，点击先探测该路径，最多 1.5 秒；否则使用新的信令与 ICE。服务端在设备证明完成后分配角色，不依赖 HTTP 请求顺序。仅打开会话或恢复网络不会自动重连，失败后等待再次点击。

缓存 IP 无法单独重建已关闭的 WebRTC 连接：旧端口、ICE 凭证和 NAT 映射都可能失效。上次路径复用仅限休眠保留 30 秒的现存已认证 Socket，不改写候选，也不绕过 ICE 安全校验。不使用 TURN 时，部分 NAT/防火墙组合仍无法直连。

双方不再持有同一套配对命名空间与恢复令牌、任一设备私钥已经变化，或只在一侧重新配对导致另一侧仍保存旧身份时，恢复都无法成功。如果清过站点数据、使用隐私模式、拒绝存储授权或浏览器回收了存储，需要重新配对。

## 手机接收文件失败

Peerto 优先把接收数据流式写入 OPFS，不要求 Android 先创建目标文件。检查：

- 浏览器可用磁盘空间
- 站点存储权限和配额
- 页面是否在传输中被系统挂起
- 两端是否保持在前台
- 文件是否超过 `MAX_FILE_BYTES`

浏览器不支持 OPFS 时会退回内存和普通下载。大文件在该模式下更容易被系统终止。

当前协议不支持断点续传。传输中刷新、断网或关闭页面后，需要重新发送文件。

## TURN 配置后没有看到 relay

只要直连可用，ICE 选择直连是正常的。确认 TURN 是否参与可以查看：

- Chrome 的 `chrome://webrtc-internals`
- Firefox 的 `about:webrtc`
- coturn 容器日志

如果没有 relay Candidate，检查 TURN 域名、端口、传输类型、用户名、密码、防火墙和 `external-ip`。TURN 主机在 NAT 后时，relay 端口范围必须一对一映射。

## 页面出现人机验证失败

Turnstile token 有效时间短且只能使用一次。刷新页面后重试。如果持续失败，站点运营者应检查：

- Widget 是否允许当前 hostname
- 服务端的 site key 和 secret 是否属于同一个 Widget
- `TURNSTILE_ALLOWED_HOSTNAMES` 是否包含当前域名
- CSP 是否允许 `https://challenges.cloudflare.com`
- 服务端是否能访问 Siteverify

不要把 Turnstile secret 发到 Issue。

## 收集诊断信息

提交 Issue 时可以附上：

- 浏览器名称与版本
- 操作系统
- 两端网络类型，例如家庭 Wi-Fi、移动网络或公司网络
- 页面显示的连接阶段和错误码
- 是否配置 TURN
- 能否在其他网络重现

不要附上：

- 连接码或分享链接
- 恢复令牌
- TURN 密码
- Turnstile secret
- 完整 SDP、ICE Candidate 或真实 IP
- 浏览器站点存储导出
